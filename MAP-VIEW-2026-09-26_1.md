## 2. Data

- **Property table:** `public.properties`. The map uses the Properties page's own query, so there is one data source:
  - `publish_status = 'Published'`, which RLS also enforces for visitors
  - plus every filter
  - Drafts never appear. Tested with a Draft that has coordinates.
- **Coordinate fields found on the live database:** none. The only location field is free-text `location`.
- **Schema change required:** yes. `migration-2026-09-26-06-property-coordinates.sql`:
  - adds `latitude numeric(9,6)` and `longitude numeric(9,6)`, both nullable
  - adds one CHECK: both empty, or both filled with valid ranges, and not 0,0
  - no policy, grant, function or trigger changes. The columns follow the existing property policies.
  - safe to run twice, and has a rollback.
  - Tested on a copy of production: only the two columns appear, all existing property data is byte-identical, and the rollback returns the schema exactly.

## 3. Google Maps setup (you do this; no key was created or invented)

1. **Google Cloud Console:** create or choose a project with **billing enabled**, then enable **Maps JavaScript API**.
2. **Create a key:** APIs & Services → Credentials → Create credentials → API key. Then restrict it:
   - **Application restriction: Websites.** Add `https://aventrixrealty.com/*` and `https://www.aventrixrealty.com/*`.
   - **API restriction:** Maps JavaScript API only.
3. **Put the key in `js/maps-config.js`:** `apiKey: "…"`. This is the same pattern as `js/supabase-client.js`. The site has no build step or server-side environment, so there is no environment variable to set.
   - A Maps JavaScript key is visible in the browser by design. The restrictions above are what protect it.
   - Never put a server key or the Supabase service-role key there.
4. **Optional:** Google Cloud → Map Management → create a **Map ID** (JavaScript, vector) and set `mapId: "…"`.
   - Markers then use Google's current Advanced Markers.
   - Without a Map ID, classic markers are used. Google marked these deprecated in 2024 but still supports them.
5. **Coordinates:** Admin → Properties → edit → **Map location**.
   - In Google Maps, right-click the exact spot and click the numbers (e.g. `12.9416, 80.1984`) to copy them.
   - Paste into Latitude; both boxes fill.
   - Leave both empty to keep a property off the map.

## 4. How it works

- **Markers:** created once per property, only for rows with valid coordinates. They are reused when filters change; they are not recreated.
  - When filters change, markers are shown or hidden in place.
  - Pins use the brand green with a gold dot.
- **Clustering: yes**, built in (no extra library).
  - Markers closer than about 46 px merge into a numbered bubble.
  - Clicking a bubble zooms in to its members.
  - Properties at the same spot open as a paged preview (1 / 2, ‹ ›).
- **Preview:** built from the property record:
  - image, title, location
  - type / BHK / For Sale–Lease, area, price
  - Wishlist and Shortlist (same property ID; the list card updates too)
  - **View Details** (`property.html?id=<slug>`)
  - Phones: a bottom sheet inside the map. Desktop: a card in the map's corner.
- **Filters:** `properties-search.js` runs the one query plus the client-side filters, then publishes the final array.
  - List View renders it as cards; Map View places the same array.
  - The count is the same number for both.
  - If some results have no coordinates, the map shows "Showing X of Y properties on the map. Some properties are not currently available on the map — see List View." This is hidden when all have coordinates.
- **Bounds:** when opened, and after each filter change, the map fits all visible markers. With a single property it centres on it at street level (zoom 15).
- **Search this area: implemented.** After you pan or zoom, a button applies the visible area as one more filter in the same pipeline.
  - This means no new database request.
  - List, map and count update together, and a "Map area ✕" chip clears it.
  - The map state is never put in the URL, so there are no duplicate URLs; `properties.html` stays canonical.
- **Without coordinates:** those properties are never placed (no guessed or city-centre markers) and stay in List View. If none of the results has coordinates, no map is drawn, only the message.
- **Floating WhatsApp / Back-to-top:** they fade out while they would sit on the map or its preview, and return when the map is scrolled away. The site has no floating Call button.
- **Loading:** Google Maps is requested only when Map View is first opened, once per page view. The page reopens in the last view chosen in this browser tab.
- **Failures:** the fallback message "Map view is temporarily unavailable. Please use List View to browse properties." covers:
  - no key
  - an invalid or restricted key (Google's `gm_authFailure`)
  - a script network error
  - a 15-second timeout
  - List View keeps working in every case.
- **Google terms:** Google's own tiles, controls and attribution are used unchanged. Nothing from Google is stored or copied.

## 6. Limitations / for your review

1. **Real Google Maps is untested here** because the sandbox has no network access to Google. Check it once with your key.
2. **Coordinates:** 0 of the 25 live properties have them, because the columns don't exist yet. They must be added per property in Admin after migration 06.
3. **Existing behaviour, unchanged:** if Supabase is completely unreachable, the Properties page keeps showing "Loading properties…" instead of its error message. The previous build does the same; the map simply stays hidden.
4. **Near Me:** it still estimates distance from locality centres (existing feature). It could switch to the real coordinates once enough properties have them.
5. **Who can edit coordinates:** the same people who can already edit a listing's other details. That is Admin, the customer who submitted it (while it's theirs), and the assigned realtor. Publishing stays Admin-only (existing guard).
